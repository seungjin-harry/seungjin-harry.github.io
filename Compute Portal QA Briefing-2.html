2Objectives & scope

Why we are testing

  • Human perspective: can a first-time developer sign up, understand the price, deploy and stay in control of spend without help?
  • AI-agent perspective: can an autonomous agent operate the platform correctly (parse results, detect failures), safely (no unapproved spend, no secret leakage) and efficiently?
  • Evidence for decisions: turn impressions into measurable KPIs with targets, so improvements can be tracked release over release.

In scope

  • Web portal: landing, sign-up, dashboard, pricing, docs
  • cpctl CLI: 59 top-level commands, help, queries, error handling
  • Agent surfaces: llms.txt, MCP server (mcp.computeportal.io)
  • Billing and payment information paths (read-only so far)

Not yet covered

  • Real deployments, GPU jobs, billing accuracy, cancellation and refunds (these need a paid plan)
  • MCP server behavior; agent task trials
  • Load and performance testing (out of scope by design)

3Approach & phase gates

Each phase must be completed before the next one starts. Phases that cost money run only with explicit approval and a defined budget.

P0 · DONE

Read-only verification

Automated probe: every query × 3 output modes, invalid inputs, cross-command consistency, repeatability, a 10-call burst, credential storage check. Plus manual web UX tasks and SUS.

P1 · NEXT

Free actions & agent trials

11 CLI agent tasks (including 3 adversarial safety tasks), 6 MCP tasks, API-key create/revoke, environment-variable token test. Cost: USD 0.

P2 · NEEDS DECISION

Cost-controlled lifecycle

Cheapest low-end plan for one month: deploy, logs, metrics, redeploy, rollback, delete, bill reconciliation, then cancel before renewal.

P3

Autonomous agent

The agent receives only goals, works within the P2 budget under supervision, and is scored on success, intervention rate and unsafe-action rate.

Method principles

  • Pass/fail is decided by a script wherever possible (JSON parser, exit codes, timing), not by eye.
  • Observed facts and hypotheses are labeled separately. A feature described in help but not executed is never marked as passing.
  • Every automated run records exit code, stdout and stderr separately, latency and the environment.
  • Secrets (tokens, e-mails, IDs) are masked automatically in all artifacts.
  • Severity: S1 critical (money, data, blocked core flow), S2 high (an agent or user is likely to decide wrongly), S3 medium, S4 low.
  • For agents, a silent failure is rated one level more severe than a visible error.

4KPI framework (40 KPIs)

AI agent (17)

  • JSON output coverage; flag-position independence
  • Exit-code accuracy; stderr separation; structured errors
  • No ANSI codes in piped output; no hang when run non-interactively; help completeness
  • Cross-command consistency; rate-limit transparency
  • Discoverability (llms.txt, MCP, docs, OpenAPI, pricing)
  • Pre-execution cost estimate; idempotency
  • Task success rate, human-intervention rate, unsafe-action rate (target 0%), step efficiency

Human user (8)

  • Time to first login (target ≤ 5 min); time to first deploy (target ≤ 15 min)
  • SUS usability score (target ≥ 80, acceptable ≥ 68)
  • Price comprehension (answer a price question in ≤ 2 min)
  • Web ↔ CLI information match (target 100%)
  • Error-message actionability; accessibility (≥ 90); web performance

Operations (7)

  • Query latency p50 / p95 (≤ 1 s / ≤ 3 s)
  • Query success rate (≥ 99%); rate-limit errors at normal pace (0%)
  • Deploy success and time; log/metric visibility delay
  • Clean-up completeness (0 orphaned resources); rollback success

Security & cost (8)

  • Credential storage (0600 file permissions, no plaintext); token input without command-line arguments
  • Scoped API keys and per-key spend limits
  • No internal or other-tenant data exposed
  • Billing accuracy ≤ 1%; failed or cancelled job billing matches policy
  • Expired payment tokens rejected; paid actions refused before charge when no plan or funds

Full definitions, formulas and targets: 02_test_plan_kpi.md in the test package.

7Strengths worth keeping

Agent-first intent

An llms.txt with a clear install → login → deploy flow, an MCP server with 21 tools, and device-code login where a person approves once. Few competitors ship all three.

Clean CLI mechanics

Errors go only to stderr, there are no ANSI codes in pipes, nothing hangs when run non-interactively, p95 latency is 1.3 s, and the CLI has 59 commands covering deploy, data, network, GPU and billing.

Safe default on missing plan

A paid action without a plan is refused before any charge, with a precise HTTP code (402) and a link to fix it.

Readable errors

Human testers rated error messages 5/5. They name the resource and include usage and an example.

Accessibility

Lighthouse accessibility is 94–100 on all pages measured.

Price position

A clear value proposition (about 30% under equivalent AWS pricing), stated on the first screen and in llms.txt.

8Recommendations

Now (days)

  • Fix the sign-up "Validation failed" error and show the failing field.
  • Use one data source for balance and for GPU counts across web, CLI and API.
  • Return a non-zero exit code for unknown subcommands and invalid region, type or period values.
  • Make the CLI defaults and examples use GPU types that are actually sold.
  • Use the same billing wording everywhere (per-second vs monthly).
  • Fix the error text that says cp login; it should be cpctl login.

Next (weeks)

  • Honor --json on every command, including JSON error objects with code, message and retryable.
  • Add --dry-run or a quote to every cost-incurring command, and require --yes to commit spend.
  • Offer scoped API keys (read-only, deploy-only) with per-key spend caps and expiry.
  • Store the token in the OS keychain, read it from CP_API_TOKEN, and add token expiry.
  • Add exit codes, error codes, rate limits and the cost-confirmation protocol to llms.txt.
  • Redirect /docs to the docs site, and fix dashboard performance (Lighthouse 39).

Strategic

  • Agent-safe billing: per-agent budgets, approval tokens for spend (extend pay authorize), and renewal notices that require confirmation.
  • Hourly or trial options so that users and agents can evaluate without a monthly commitment.
  • Publish an OpenAPI spec and a versioned JSON output schema as a public contract.
  • An "Agent-Ready" conformance suite in CI, re-using this test harness.

Decisions requested

  1. Phase P2 budget: fund one month of the cheapest plan (or provide test credits or a sandbox org) for lifecycle and billing tests.
  2. Fix priority: agree on the "Now" list (sign-up, balance, exit codes, defaults, billing wording) and a retest date.

Clarifications needed from the team
